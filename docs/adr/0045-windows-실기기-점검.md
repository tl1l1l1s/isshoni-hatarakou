# 0045 Windows 실기기 점검

날짜 2026년 10월 18일

친구 PC와 같은 실제 Windows PC에서 `docs/checklists/windows-m0.md`를 확인했습니다. 설치 파일은 이 PC에서 빌드하지 않고 GitHub Releases의 v0.1.1과 v0.1.2를 받아 썼습니다(v0.1.2는 main d21a5c7). 처음에는 v0.1.2 설치 파일로 설치됐고, 이를 지우고 데이터 폴더를 옮긴 뒤 v0.1.1을 깨끗이 설치했습니다. 그 v0.1.1이 v0.1.2로 올라가는 과정으로 자동 업데이트를 처음 실제 기기에서 봤습니다.

두 번째 기기는 Mac 대신 같은 PC에서 설치판을 `--user-data-dir`로 하나 더 켜고 시험 계정으로 같은 방에 넣었습니다. 누르기, 끌기, 휠, 키 입력은 SendInput으로 만든 OS 입력으로 했고 펜은 쓰지 않았습니다. 시험 준비로 설정 체크 상자를 바꾸는 것처럼 클릭 자체를 보지 않는 조작은 UI Automation으로 눌렀습니다. 화면 요소의 자리와 상태는 UI Automation과 Win32 API로 읽었습니다. 괄호 안 숫자는 점검표의 줄 번호입니다.

### 실패와 재현 순서

1. **숨겼다 다시 보인 실행 화면이 왼쪽 클릭을 받지 않습니다.** 점검표 36, 37은 숨고 보이는 것만 봐서 통과로 적었습니다.
   1. 0.1.2 실행 화면에서 `메뉴 ▼`를 눌러 메뉴가 열리고 닫히는 것을 봅니다.
   2. `Ctrl+Alt+H`로 숨기고 3초 뒤 `Ctrl+Alt+H`로 다시 보입니다.
   3. 캐릭터 몸, 이름표, `메뉴 ▼`, 상태 칩을 왼쪽 클릭해도 💗, 메뉴, 상태 고르기 창이 뜨지 않습니다. 커서를 올리면 클릭 통과는 풀리고 툴팁도 뜹니다.
   4. 캐릭터를 오른쪽 클릭하면 메뉴가 열리고 그 뒤로는 왼쪽 클릭도 됩니다.

   트레이 아이콘, 회사원 모드 [숨기기] 칩, 전체 화면 판정(바탕화면, Win+D), 가상 데스크톱 왕복으로 숨었다 보일 때도 같고, 숨기지 않아도 화면을 잠갔다 풀면 같습니다. 그동안 스테이지의 자식 창 `Chrome_RenderWidgetHostHWND`가 숨김 상태입니다. 스테이지 창 크기가 바뀌면(메뉴 열기, 캐릭터 크기, 방 인원) 돌아오고 기다리거나 다시 숨겼다 보여도 돌아오지 않습니다. 자세한 것은 진행 메모에 있습니다.
2. **바탕화면이 앞 창이면 캐릭터가 숨습니다(54 실패의 원인).**
   1. 기본 설정(`전체 화면 앱 위에서 숨기기` 켜짐)으로 실행 화면을 띄웁니다.
   2. 바탕화면 빈 곳을 누르거나 Win+D를 누릅니다. 1초 안에 실행 화면이 숨습니다.
   3. 다른 앱을 앞으로 가져오면 3초 안에 다시 보입니다. 이때 1번 문제도 생깁니다.

   `checkCover`(`src/main/windows/manager.ts:306`)는 앞 창의 위치와 크기가 캐릭터 모니터 영역과 모두 1px 안에서 같으면 전체 화면 앱으로 봅니다(이 앱과 펜 입력 보호 앱만 뺌, `:309-310`). 바탕화면 창(WorkerW, 0,0 1920x1080)이 여기에 맞습니다. 빈 새 가상 데스크톱으로 가도 앞 창이 바탕화면 창이 되어 캐릭터가 보이지 않습니다.
3. **`no-gpu`로 켜면 실행 화면이 그려지지 않습니다(77).**
   1. `%APPDATA%\isshoni-hatarakou`에 확장자 없는 빈 파일 `no-gpu`를 만들고 앱을 켭니다.
   2. 진단 요약에는 `하드웨어 가속: 꺼짐`이 보입니다.
   3. 캐릭터, 이름표, 칩이 화면에 없습니다. 보이지 않는 칩 자리에 커서를 두면 클릭을 가로채고, 누르면 그 칩의 창이 열립니다.
   4. 파일을 지우고 다시 켜면 돌아옵니다.

   원인: 앱을 켜면 스테이지를 만들 때(`src/main/windows/manager.ts:372`의 `applyOpacity()`) 렌더러가 설정을 보내기 전이라 `opacity252`가 `false`(`:92`)이고, 플랫폼 어댑터의 `setOpacity252`(`src/main/platform/win/index.ts:56-59`)가 `setOpacity(1)`을 불러 스테이지에 `SetLayeredWindowAttributes`가 걸립니다. 뒤이어 깜빡임 줄이기 켜짐 값이 와도 GPU 합성이 꺼져 있으면 어댑터가 아무것도 하지 않으므로, 환경 변수 `ISSHONI_OPACITY_252=1`일 때만 빼고 이 설정과 관계없이 같습니다. 하드웨어 가속이 꺼진 Chromium은 투명 창을 `UpdateLayeredWindow`로 그리는데 이 호출이 그런 창에서는 실패합니다. 스테이지의 `WS_EX_LAYERED`를 껐다 켜서 그 상태를 지우자 캐릭터가 바로 그려졌습니다.
4. **Windows 10에서 🫧와 🪄가 빈 네모로 보입니다(91).**
   1. 설정 계정 탭의 닉네임 끝에 `🫧🪄`를 넣고 [저장]을 누릅니다.
   2. 설정 창 입력란과 실행 화면 이름표에 `□□`가 보입니다.

   이 PC의 컬러 이모지 글꼴 `seguiemj.ttf`에 두 글자(이모지 13, 14)가 없습니다. 앱은 이모지 글꼴을 싣지 않습니다.
5. **패널 창이 선언한 크기보다 26px 높습니다(61에 영향).**
   1. 1920x1080 배율 100%에서 앱을 켜 런처를 띄웁니다.
   2. 380x600으로 선언한 런처의 클라이언트 영역이 380x626입니다. 대화하기(360x600)도 1366x768과 1280x720에서 360x626이었습니다.
   3. 작은 화면에서는 창 아래 끝이 작업 영역보다 1366x768에서 19~26px, 1280x720에서 2~19px 내려가 작업 표시줄 뒤에 들어갑니다.

   원인: 패널은 `window.open`과 `overrideBrowserWindowOptions`(`useContentSize: true`)로 만들고 `did-create-window`에서 `removeMenu()`를 부릅니다(`src/main/windows/manager.ts:411`, `:436`). Windows에는 Electron 기본 앱 메뉴가 그대로 있어서(앱 메뉴는 Mac에서만 바꿈) 메뉴 막대 높이를 더해 만든 창 크기가 `removeMenu()` 뒤에도 남습니다. 같은 Electron 44.7.0으로 같은 방식의 작은 스크립트를 돌려 재현했고, 창을 만들기 전에 `Menu.setApplicationMenu(null)`을 부르거나 `overrideBrowserWindowOptions`에 `autoHideMenuBar: true`를 넣으면 380x600이 됐습니다.

### 확인이 필요한 것

- **대화하기 입력란(60):** ▼ 메뉴로 연 대화하기 창은 앞 창이 되지만 입력란에 커서가 없어 바로 친 글자가 들어가지 않습니다. 입력란에 `autoFocus`가 없습니다. 점검표의 "바로 글자를 입력할 수 있습니다"가 입력란을 누르지 않고 친다는 뜻이면 실패입니다.
- **작업 영역을 넘는 창(61):** 1366x768에서 스티커 사진, 캐릭터 만들기, 대화하기 창은 화면 안에 열리고 단추도 보였지만 창 아래 끝이 작업 영역보다 19~26px 아래로 내려가 작업 표시줄 뒤에 들어갔습니다. 1280x720 100%에서는 [촬영 시작]과 [저장]의 아래 6px가 작업 표시줄에 가렸습니다. 이 모니터는 1280x720에서 배율 150%를 고를 수 없어 그 조합은 보지 못했습니다. 26px은 실패 5번 때문이고, 작업 영역에 맞춰 줄인 창이 19px 커지는 까닭은 확인이 필요합니다.
- **닿은 직후 누르기(17):** 멀리서 커서를 한 번에 옮겨 캐릭터에 닿은 뒤 0ms, 20ms, 50ms, 100ms에 누르면 20번 중 12, 1, 2, 0번 아래 창에 점이 찍혔고, 55ms 동안 12단계로 옮기면 0ms에 11번, 30ms와 60ms에는 0번이었습니다. 클릭 영역에서 40px보다 멀면 클릭 통과를 50ms마다 보므로(`src/shared/constants.ts:44-46`, `src/main/clickthrough.ts:22-23`) 한 번에 옮긴 뒤 50ms 안에 누르면 아래 창으로 갈 수 있습니다. 20번 시험의 꺼지는 시간(중앙 51ms)도 이 결과와 맞지 않아 잰 방법을 다시 봐야 합니다. 사람 손으로 빠르게 옮겨 누른 시험에서는 몸 위 클릭이 한 번도 새지 않았습니다(아래 진행 메모). 점검표 항목은 이 결과로 체크했고, 자동 입력에서만 보인 50ms 틈은 남겨 둡니다.
- **업데이트 상태 `확인 전`:** 최신 버전이라 받을 것이 없는 기기도 진단 요약과 기기 기록의 업데이트 상태가 계속 `확인 전`입니다. `ops.ts versions`로 확인을 못 한 기기와 가를 수 없습니다.
- **업데이트 캐시:** 업데이트 뒤 `%LOCALAPPDATA%\isshoni-hatarakou-updater`에 설치 파일이 두 벌(각 118MB) 남고, 앱을 지워도 이 폴더는 남습니다. 설치 안내의 삭제 절차에 이 폴더가 없습니다.
- **▼ 메뉴 [종료] 무반응(129 시험 중):** 핀을 켠 플레이리스트에 소개글을 친 직후 ▼ 메뉴의 [종료]를 마우스로 누르자 두 번 아무 일도 없었습니다. 다시 만들지 못했습니다.
- **날짜 칸 구분자(63 시험 중):** 순서는 연 월 일이지만 Mac(0032)의 `2026. 10. 31.`과 달리 `2026-10-19`처럼 `-`로 나눕니다.
- **맞춤법 사전 내려받기:** `webPreferences.spellcheck: false`(`src/main/windows/manager.ts:358-359`, 0025)를 두었는데도 첫 실행 때 `redirector.gvt1.com`에서 `ko-3-0.bdic`(11MB)를 받아 데이터 폴더에 둡니다. 창마다 끄는 것으로는 세션의 맞춤법 검사기가 사전을 받는 것을 막지 못하는지 확인이 필요합니다.

### 진행 메모

- 첫 설치는 v0.1.1이 아니라 v0.1.2 설치 파일로 됐습니다(다운로드 폴더에 `isshoni-hatarakou-Setup-0.1.2.exe`). 로그에 `Update for version 0.1.2 is not available (latest version: 0.1.2, downgrade is disallowed)`가 남았고 업데이트 안내가 뜨지 않은 것은 맞는 동작입니다.
- 이때 확인을 마친 뒤에도 진단 요약의 업데이트 줄이 `확인 전`으로 남았습니다. `src/main/updater.ts`는 `error`와 `update-downloaded`만 들어서 최신 버전인 기기는 계속 `확인 전`이고 `boot.tsx`가 기기 기록 `upd`에도 이 값을 씁니다. `ops.ts versions`에서 최신이라 받을 것이 없는 기기와 확인을 아직 못 한 기기를 가르지 못합니다.
- 이 PC의 다운로드 폴더 파일 다섯 개에 모두 Mark-of-the-Web(`Zone.Identifier`)이 없습니다(기본 브라우저 Chrome). 이 상태로는 SmartScreen이 뜨지 않으므로 SmartScreen 항목은 Edge와 Chrome이 보통 PC에서 붙이는 것과 같은 `ZoneId=3` 표시를 설치 파일에 붙여 시험했습니다(아래 107, 108).
- v0.1.1에서 v0.1.2로 차등 업데이트를 받으면 blockmap 비교로 164블록, 3,365,802바이트(설치 파일의 2.7%)를 새로 받습니다.
