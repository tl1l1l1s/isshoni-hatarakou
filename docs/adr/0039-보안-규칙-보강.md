# 0039 보안 규칙 보강

날짜 2026년 10월 12일

보안 검토에서 나온 규칙 문제 세 가지 가운데 두 가지를 고쳤습니다. 공개 프로필 `users/{uid}/public`과 계정 접속 상태 `users/{uid}/presence/m`은 정하지 않은 칸을 크기 제한 없이 받았습니다. 공개 프로필은 발급받은 계정이 모두 읽으므로 한 계정이 큰 기록을 올리면 그 프로필을 읽는 사람이 모두 내려받습니다. 규칙은 멤버 기록의 `joinedAt`과 `seenAt`이 숫자인지만 검사해서 미래 시각도 들어갔습니다. 미래 `seenAt`을 쓴 기록은 150초가 지나도 오래된 기록이 되지 않아 다른 멤버가 지우지 못했습니다. 세 번째 문제인 디스코드 웹훅 주소는 선물하는 사람이 정할 일이라 바꾸지 않았습니다. 0020의 알려진 한계 가운데 공개 프로필의 m을 검사하지 않는다는 항목을 이 문서가 바꿉니다.

## 정한 것

- 공개 프로필은 계정 발급 스크립트와 앱이 쓰는 칸만 받습니다. `v`는 1이어야 하고 `name`은 1자부터 20자까지의 글이며 `friendCode`는 예전처럼 지금 값과 같아야 합니다. `m`은 아래 모듈 필드 검사를 따르고 나머지 칸은 `$other`로 거부합니다. 이름을 1자부터 받는 것은 account 모듈 `cleanName`과 같습니다.
- 멤버 기록, 공개 프로필, 계정 접속 상태의 m은 모듈 필드 검사 `MODULE_FIELDS`(`rules/core.ts`)를 함께 씁니다. 멤버 기록에 있던 검사를 옮겨 왔습니다. 모듈 id와 필드 이름은 32자까지이고 값은 128자 이하 글, 숫자, 참거짓이거나 그런 값을 담은 한 단계 객체입니다. 배열은 숫자 키 객체로 저장되므로 chat 이모티콘 목록도 한 단계 객체입니다. m 자체도 객체여야 한다는 조건을 더했습니다.
- 멤버 기록의 m과 mods는 객체만 받습니다. 예전 규칙에서는 m이나 mods 자리에 글 하나를 쓰면 칸마다 하는 크기 검사가 적용되지 않아 1만 자 글이 들어갔습니다. 두 자리 모두 에뮬레이터에서 확인했습니다.
- 멤버 기록의 `seenAt`은 서버 시각만 받습니다(`newData.val() === now`). 앱은 늘 서버 시각으로 씁니다. 입장, 다시 연결, 넘기기 뒤 다시 들어가기는 `register`가 serverTimestamp로 쓰고 60초마다 쓰는 하트비트(`RoomSession.tick`)는 `SERVER_TIME`으로 씁니다. 이름이나 상태 같은 코어 필드와 모듈 필드는 `seenAt` 없이 update로 씁니다. 규칙은 이번 쓰기에 든 칸만 검사하므로 이 쓰기는 그대로 통과합니다. 에뮬레이터에서 확인했습니다.
- 멤버 기록의 `joinedAt`은 서버 시각보다 60초(`JOINED_SKEW_MS`) 넘게 앞서지 못합니다. 앱은 `joinedAt`을 서버 시각 표시가 아니라 `time.serverNow()`로 정합니다. 이 값은 PC 시계에 연결할 때 받은 서버 시각 차이를 더한 것이라 연결한 뒤 PC 시계가 앞으로 맞춰지면 그만큼 서버 시각보다 앞섭니다. 60초는 0020에서 채팅 메시지 키에 준 1분과 같은 여유입니다. 60초 안의 미래 값으로 얻는 것은 좌석 순서가 그만큼 뒤로 가는 것뿐입니다. 다시 연결되면 앱이 처음 `joinedAt`을 다시 쓰므로 지난 값은 막지 않습니다.
- 메모리 서버도 두 시각을 확인합니다. `checkMember`는 미래 `joinedAt`을 거부하고 `writeMine`은 서버 시각 표시가 아닌 `seenAt`을 거부합니다. 규칙이 거부할 쓰기는 메모리 서버를 쓰는 시뮬레이터 시험과 e2e 시험에서도 실패하게 하려는 것입니다. 공개 프로필과 계정 접속 상태의 모양 검사는 메모리 서버가 예전부터 따라 하지 않던 규칙이라 더하지 않았습니다.

## 쓰는 곳

- 공개 프로필은 세 곳이 씁니다. `scripts/create-account.ts`가 관리 SDK로 `{ v: 1, name, friendCode }`를 만들고 코어 `writeName`(닉네임 저장과 처음 이름 올리기)이 `name`을 update로 씁니다. `ctx.self.setProfile`은 `m/<모듈 id>`를 쓰고 지금은 growth의 `level`(1부터 999까지)과 chat의 `emo`(파일 해시 8개까지)뿐입니다. `scripts/ops.ts`는 읽기만 합니다.
- 계정 접속 상태는 `presence.start`가 `{ online, lastSeen, m }` 전체를 쓰고 `presence.set`이 `m/<모듈 id>` 하나를 씁니다. 끊길 때의 예약 쓰기는 `online`과 `lastSeen`만 씁니다. m에 들어가는 값은 manifest `accountPresence`에 선언한 rooms의 `code`와 friends의 `hidden`뿐입니다.
- 멤버 기록의 `joinedAt`은 `RoomSession.enter`가 들어갈 때 `time.serverNow()`로 정합니다. 넘기기 뒤 다시 들어가기도 새로 들어가는 것이라 이때 다시 정합니다. 다시 연결과 `recover`는 `register`로 기록 전체를 다시 쓰면서 처음 `joinedAt`을 그대로 씁니다.
- 0.1.0 코드의 같은 자리도 확인했습니다. 쓰는 칸과 값 모양이 지금과 같아서 새 규칙을 통과합니다.

## 배포

- 규칙은 앱과 따로 올립니다. 이번 앱 업데이트를 낼 때 `npm run rules:deploy`로 새 규칙을 함께 올려야 운영 서버에 보강이 적용됩니다.
- 새 규칙이 거부하는 칸을 쓰는 예전 앱은 그 쓰기가 실패합니다. 공개 프로필의 다른 칸, PC 시계로 쓴 `seenAt`, 60초 넘게 앞선 `joinedAt`, 글 하나로 쓴 m이나 mods가 그렇습니다. 0.1.0에는 이런 쓰기가 없습니다.
- 운영 데이터에 이미 들어 있는 값은 규칙이 바꾸지 않습니다. 새 규칙에 맞지 않는 값이 있으면 그대로 남고 그 칸을 다시 쓸 때 거부됩니다. 운영 데이터는 확인하지 않았습니다.

## 정하지 않은 것

디스코드 웹훅 주소(`mod/report/g/tunables/webhook`)는 지금처럼 발급 계정이 모두 읽습니다. 고를 수 있는 방법은 세 가지입니다.

- 받아들인 위험으로 둡니다. 할 일이 없고 알림도 지금처럼 바로 옵니다. 대신 친구 누구나 주소를 읽어 그 채널에 글을 올릴 수 있고 주소가 알려지면 디스코드에서 웹훅을 새로 만들어 조정값을 바꿔야 합니다. 기기마다 `device/crash.json`에 남은 옛 주소는 앱을 켤 때나 10분마다 하는 설정 알림 때 바뀝니다.
- 디스코드로 보내지 않고 데이터베이스 기록(`mod/report/u/{uid}/r`)만 남깁니다. 선물하는 사람은 `scripts/ops.ts reports`로 읽습니다. 앱에 주소를 두지 않지만 스크립트를 실행하기 전에는 제보와 자동 오류 보고를 알지 못합니다. 렌더러가 한 번도 뜨지 못하는 오류는 메인 프로세스에만 남아 있어서 기록에 들어가지 않습니다.
- 예약 작업이 새 기록을 읽어 웹훅으로 올립니다. 주소는 그 작업에만 있습니다. GitHub Actions 예약 작업은 가장 짧은 간격이 5분이고 관리 SDK 서비스 계정 키를 저장소 비밀값에 두어야 합니다. 공개 저장소라 실행 기록에 제보 글이 나오지 않게 해야 합니다. Cloud Functions는 Blaze 요금제가 필요하고 선물하는 사람 PC의 예약 작업은 그 PC가 켜져 있어야 합니다.

## 확인한 것

- 규칙 시험 4개를 더하고 멤버 기록 모양 시험 1개를 늘렸습니다. 공개 프로필의 발급 스크립트 모양과 앱 필드 받기, 모르는 칸과 큰 값과 깊은 m 거부, 계정 접속 상태 m의 크기, 미래 `seenAt`과 `joinedAt` 거부, 입장과 하트비트와 코어 필드 update와 다시 연결과 다른 기기 키 쓰기, m과 mods 자리의 긴 글 거부입니다. 예전 규칙에서는 정상 쓰기 시험을 뺀 넷이 실패하고 새 규칙에서는 41개가 모두 통과합니다. 오래된 남의 기록 지우기는 있던 시험이 그대로 통과합니다.
- 계약 시험에 미래 `joinedAt`과 서버 시각 표시가 아닌 `seenAt` 거부를 더해 메모리 서버와 에뮬레이터가 같게 거부하는지 봅니다.
- 에뮬레이터를 가리키는 앱으로 두 계정을 실제로 썼습니다. friends 검증 지도에 적힌 대로 `VITE_FIREBASE_*`와 메인 CSP에 에뮬레이터 주소를 넣은 `--mode e2e` 빌드를 저장소 밖 사본에서 만들고 `scripts/create-account.ts`로 계정 둘을 만든 뒤 설정 코드로 로그인했습니다. 닉네임 저장, growth 레벨, 내 이모티콘 넣기(chat.emo), 방 만들기와 참여, 친구 신청과 수락, 오프라인으로 보이기 켜고 끄기, 3분 넘는 하트비트(두 기록 모두 `seenAt`이 1분 간격으로 네 번 바뀜), 끊었다 다시 연결(기록이 지워졌다가 같은 `joinedAt`으로 다시 써짐), 같은 계정의 두 번째 PC로 넘기고 `여기서 계속 쓰기`로 되찾기, 방에서 나가기(기록과 roster가 지워지고 친구 창이 접속 중으로 바뀜)를 거쳤습니다. 세 앱의 메인 로그와 콘솔에 쓰기 거부나 쓰기 실패는 없었습니다.
- 콘솔 경고는 친구 수락 직후 상대 접속 상태 전체 읽기가 한 번 거부되는 한 줄뿐이었습니다. 상대가 아직 나를 목록에 넣기 전이라 거부되는 읽기이고 0037의 한계에 적혀 있습니다. main의 규칙으로 같은 흐름을 실행해도 같은 한 줄이 나옵니다.
- `npm run typecheck`, `npm run lint`, `npx vitest run`(661개 통과, 에뮬레이터 시험 127개 건너뜀), `npm run rules:build -- --check`, 에뮬레이터 시험 전체(19개 파일, 178개, 9880번대 포트), e2e(boot, m3-core, recovery, upgrade, windows-smoke의 26개)가 통과했습니다.

## 한계

- 규칙은 자식 수를 세지 못합니다. 고친 앱은 m 아래에 작은 필드를 얼마든지 늘릴 수 있어서 공개 프로필의 크기를 완전히 막지는 못합니다. 개수까지 막으려면 쓰는 곳마다 모듈 id와 필드 이름을 규칙에 적어야 합니다.
- `joinedAt`의 지난 값은 막지 않습니다. 0 같은 지난 값을 쓴 사람은 정원이 찬 방에서 맨 앞 순서가 되고 정원 밖 순서가 된 사람의 앱이 스스로 나갑니다(rooms 모듈 `mustLeave`). 다시 연결할 때 처음 값을 다시 쓰는 경로를 살리면서 이것까지 막으려면 서버에 남는 첫 입장 시각이 필요합니다.
- 연결한 뒤 PC 시계가 60초 넘게 앞으로 바뀌면 다시 연결될 때까지 방에 들어가는 쓰기가 거부됩니다. 앱은 5초, 15초, 1분, 그 뒤로 5분마다 다시 들어가 보고 다시 연결되면 서버 시각 차이를 새로 받습니다.
- `lastSeen`과 roster 값은 여전히 숫자인지만 봅니다.
- `users/{uid}/private`과 모듈의 본인 범위 기록 여러 곳은 크기를 막지 않습니다. 본인만 읽어서 다른 사람이 받지는 않지만 저장 용량은 씁니다.
- 운영 Firebase에서는 확인하지 않았습니다. 쓰기 경로와 규칙이 쓰는 칸만 검사한다는 동작은 데이터베이스 에뮬레이터에서만 봤습니다. 앱 세션은 macOS에서만 실행했습니다.
