# 0027 자동 오류 보고

날짜 2026년 10월 10일

NFR-21과 OPS-03에 자동 오류 보고를 더했습니다. 버그 제보는 친구가 직접 써야 했고 로그는 친구 PC에만 남아서 선물하는 사람은 친구가 알아차리고 말해 주기 전에는 문제를 알 수 없었습니다. 고친 곳은 `src/main`(새 파일 `crash.ts`와 `crashReport.ts`), `src/preload/api.ts`, `src/renderer/core`(`boot.tsx`, `bridge.ts`, `types.ts`, `runtime.ts`, `coreModule.tsx`, `ui/Stage.tsx`), `src/modules/report`, 검증 지도, 명세 두 줄입니다.

## 정한 것

- 잡는 오류. 메인 프로세스의 처리하지 않은 예외와 거부는 electron-log의 errorHandler가 이미 받고 있어서 거기에 `onError`를 더했습니다. 로그에 적힌 뒤에 읽도록 한 틱 뒤에 보고를 만듭니다. 렌더러와 보조 프로세스(GPU, 유틸리티)가 끝나는 `render-process-gone`과 `child-process-gone`은 app에서 받고 `clean-exit`는 뺍니다. 스테이지가 응답하지 않아 다시 만드는 길(`windows/manager.ts`)에도 보고를 더했습니다. 렌더러는 `boot.tsx`의 `window` `error`와 `unhandledrejection` 리스너와 슬롯 조각의 Guard 경계(`Stage.tsx`)가 새 브리지 채널 `crash.report`로 메인에 알립니다. 패널 창의 화면은 portal이라 함수가 스테이지 문맥에 있어서 패널에서 난 예외도 스테이지 리스너가 받습니다. 스테이지 문맥의 함수를 패널 문서에 붙이고 패널을 눌러 확인했습니다.
- 비정상 종료. 켤 때 데이터 폴더에 `running` 파일을 두고 `will-quit`과 로그오프의 `app.exit` 앞에서 지웁니다. 켤 때 이 파일이 남아 있으면 지난 실행이 비정상으로 끝난 것이므로 새 로그가 쌓이기 전에 가장 최근 로그 파일의 끝을 읽어 `abnormal-exit` 보고를 만듭니다. 강제 종료, 전원 끊김, OS 충돌이 모두 여기에 들어갑니다.
- 보고 내용. 메인이 만듭니다. 앱 버전, OS 이름과 버전(`process.platform`과 `os.release()`), 켠 뒤 지난 분, 오류 종류와 메시지와 스택, 로그 파일의 마지막 50줄입니다. 집 폴더와 데이터 폴더는 `~`와 `<data>`로 바꾸고 `/Users/이름`과 `C:\Users\이름` 조각도 `~`로 바꿉니다. 로그에는 지금도 창 제목, 키 입력, 프로그램 이름이 없고 앞으로도 넣지 않습니다.
- 보내는 곳. 메인이 디스코드 웹훅에 바로 올립니다. `postJson`을 그대로 쓰고 1900자 안에 마지막 로그 10줄만 코드 블록으로 넣으며 멘션은 울리지 않습니다. 같은 보고를 서버 기록으로도 남기려고 메인이 메모리와 `device/crash.json`에 들고 있다가 report 모듈이 `crash.pending`으로 받아 `mod/report/u/{uid}/r`에 `[자동 오류 보고]`로 시작하는 글로 쓰고 `crash.ack`로 뺍니다. 글은 `TEXT_MAX`에서 자르고 규칙은 그대로입니다. 모듈은 setup 때와 메인이 `crash.added` 이벤트로 알릴 때 이 일을 합니다. 렌더러가 죽어도 메인이 보낼 수 있게 모듈이 웹훅 주소와 켜짐을 `crash.config`로 setup 때, 설정이 바뀔 때, 10분마다 알리고 메인이 같은 파일에 남깁니다. 서버 조정값이 setup 뒤에 오기 때문에 되풀이해 알립니다.
- 한도. 같은 서명(종류와 메시지 첫 줄)은 실행마다 한 번, 5분에 하나, 하루 20개입니다. 날짜와 수는 `device/crash.json`에 남겨 다시 켜도 이어집니다. 넘친 보고는 로그에 `보고 생략` 한 줄만 남깁니다. 들고 있는 보고는 20개까지입니다.
- 설정. report 모듈 설정 `autoReport`(기본 켜짐, 이름은 오류가 나면 자동으로 알리기)가 설정 일반 탭의 버그 제보 묶음에 보입니다. 끄면 메인이 보내지도 들고 있지도 않고 들고 있던 보고도 버립니다. 개인정보 처리방침에 오류가 나면 앱 버전, 운영체제, 최근 로그 몇 줄이 선물한 사람에게 자동으로 전해지고 설정에서 끌 수 있다는 문장을 더했습니다.
- 코어 변경. 모듈이 브리지를 직접 부르지 않으므로 `Ctx`에 `crash`(`config`, `pending`, `ack`, `onAdded`)를 더했습니다. 기능 이름이 아니라 메인이 모은 오류 보고를 다루는 일반 능력입니다. 브리지에는 `crash.report`, `crash.config`, `crash.pending`, `crash.ack` 호출과 `crash.added` 이벤트를 더했고 기존 채널은 바뀌지 않아 `BRIDGE_VERSION`은 그대로입니다. `bridge.ts`의 `reportError`가 렌더러 오류를 메인에 보내는 공통 함수입니다. Guard가 직접 로그에 적던 줄은 메인이 `[renderer]`로 적는 줄로 바뀌었습니다.
- 모듈 main.ts 방식은 쓰지 않았습니다. 10.5의 `mod:<id>:*` 채널을 받는 모듈 메인 부분은 아직 불러오는 장치가 없고 오류 잡기는 어차피 코어 메인의 일이라 코어 채널로 두었습니다.

## 확인한 것

- `src/main/crashReport.test.ts`가 경로 가리기, 본문 만들기, 디스코드 1900자 한도, 보내기 한도를 확인합니다.
- 검증 하네스에서 메인의 `net.fetch`를 디스코드 주소만 가로채고 report 조정값에 웹훅 주소를 넣은 뒤 확인했습니다. 렌더러에서 `ErrorEvent`를 내면 POST 본문이 `[자동 오류 보고] renderer.error: 시험 오류` 머리줄, 버전과 OS와 켠 시간 줄, 스택, 마지막 로그를 담은 코드 블록이고 `allowed_mentions.parse`가 비어 있으며 메모리 서버 `mod/report/u/{uid}/r`에 같은 글이 1000자 안으로 남고 `crash.pending`이 비워집니다. 같은 오류를 다시 내면 보내지 않고 로그에 `보고 생략`이 남습니다. `setTimeout` 안의 진짜 예외와 거부도 메인 로그에 닿습니다. 패널 문서에 붙인 스테이지 함수의 예외, `process.emit('uncaughtException')`(앱은 살아 있음), 스테이지의 `forcefullyCrashRenderer()`(다시 만든 렌더러가 기록), `app.emit('child-process-gone')`, 창의 `emit('unresponsive')`, `running` 파일과 로그를 복사한 폴더로 다시 켜기(지난 실행의 로그 줄이 기록에 들어감)를 각각 확인했습니다. 설정을 끄면 메인이 받아도 보내지 않고 들고 있지도 않으며 다시 켜면 보냅니다.
- `npm run typecheck`, `npm run lint`, `npx vitest run`, `npm run rules:build -- --check`, 에뮬레이터 규칙 시험 전체, e2e 세 개(boot, m3-core, windows-smoke)가 통과했습니다.

## 한계

- 비정상 종료 보고가 디스코드로 가는 것은 하네스에서 확인하지 못했습니다. 켜자마자 보내서 `net.fetch`를 가로채기 전에 나가므로 웹훅 주소를 비운 폴더로 켜고 서버 기록만 봤습니다.
- 로그 50줄은 디스코드에는 10줄, 서버 기록에는 1000자 안에 드는 만큼만 남습니다. 전체 로그는 전처럼 진단 기록 폴더를 받아야 합니다.
- 웹훅 주소를 처음 받기 전(첫 실행의 10분 안)에 난 오류는 디스코드로 가지 않고 서버 기록에만 남습니다.
- 렌더러가 죽은 채로 끝나면 들고 있던 보고는 다음 실행 때 기록합니다. `device/crash.json`은 1초 뒤에 쓰므로 그 안에 끝나면 그 보고는 사라집니다.
- 메인 프로세스가 죽는 경우는 그 실행에서는 잡지 못하고 다음 실행의 비정상 종료 보고로만 압니다.
- 실제 디스코드, 실제 Firebase, Windows에서는 확인하지 않았습니다.
