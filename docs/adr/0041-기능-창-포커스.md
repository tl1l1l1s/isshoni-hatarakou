# 0041 기능 창 포커스

날짜 2026년 10월 16일

v0.1.1에서 레벨 보상, 포커스 기록, 다가오는 일정 창을 한 번 열면 닫을 수 없다는 제보가 왔습니다. 세 창은 `ui.windows`에 `focusable`을 주지 않아서 기본값인 포커스를 받지 않는 창으로 열렸습니다. 이 문서는 기능 창을 모두 포커스를 받는 창으로 바꾼 이유와 확인한 것을 적습니다. 10장의 패널 규칙(키보드 입력이 필요한 창만 포커스를 받는다)을 이 문서가 바꿉니다.

## 원인

- 이 창들은 제목 표시줄의 ×와 ESC로만 닫혔고 창 안에 닫기 단추가 없었습니다. ESC는 키보드 포커스를 받은 창에만 들어가므로 이 창들에서는 처음부터 듣지 않았습니다.
- Windows 11에서는 `focusable: false` 창의 제목 표시줄로 최소화, 최대화, 끌기가 되지 않는다는 Electron 이슈가 있습니다(electron/electron#42282). × 단추도 같은 제목 표시줄에서 받는 입력이라 함께 막힌 것으로 봅니다. Windows PC에서 직접 재현하지는 않았습니다.
- 같은 기본값으로 열리던 창은 레벨 보상, 포커스 기록, 기록 미니 창, 다가오는 일정, 달성표, 우편함, 업데이트 소식, 보관함, 이모티콘, 자리비움 안내, 캐릭터 맞추기 11개입니다.
- 이 Mac에서 세 창을 열고 메인의 `BrowserWindow.close()`를 부르면 셋 다 닫혔습니다. 렌더러의 닫기 경로(`beforeunload`와 `ctx.ui.guard`)는 닫기를 막지 않았습니다.

## 정한 것

- `WindowDecl.focusable`과 `win.prepare`의 `focusable` 값을 없앴습니다. 패널은 모두 포커스를 받는 창으로 만듭니다. 고르는 값을 남겨 두면 새 창을 더할 때 같은 일이 다시 생길 수 있어서 두지 않습니다.
- 키보드 포커스를 주는 규칙은 0032 그대로입니다. 사용자가 누르거나 키를 쳐서 연 창에만 `focus()`를 부르고 모듈이 저절로 연 창은 `showInactive`와 `moveTop`으로 맨 위에 보이기만 합니다.
- 사용자가 기능 창 안을 누르면 그 창이 포커스를 가져가서 그리던 앱이 키보드를 잃습니다. 그리던 앱을 다시 누르면 돌아옵니다. 그 대신 Windows에서 모든 기능 창을 제목 표시줄의 ×로 닫고 끌어 옮길 수 있고 창을 누른 뒤에는 ESC로도 닫힙니다.
- 포커스를 받지 않는 창은 그대로 두고 창 안에 닫기 단추를 그리는 방법도 생각했습니다. 키보드를 뺏지 않는 대신 Windows에서 창을 끌어 옮기지 못하는 문제가 남아서 고르지 않았습니다.
- 실행 화면과 효과 창은 지금처럼 포커스를 받지 않습니다.

## 확인한 것

- 이 Mac에서 e2e 빌드를 켜고 확인했습니다. 레벨 보상과 포커스 기록은 ▼ 메뉴로 열고 다가오는 일정은 스케줄러에 오늘 일정을 넣은 뒤 🔔로 열었습니다. 달성표, 보관함, 우편함, 업데이트 소식, 기록 미니 창, 자리비움 안내는 코어 함수로 열었습니다. 실행 화면을 뺀 모든 창의 `isFocusable()`이 true이고 세 창은 메인의 `close()`로 닫혔습니다.
- 열려 있는 포커스 기록을 ▼ 메뉴로 다시 열면 `showInactive`, `moveTop`, `focus` 순서로 불립니다.
- 마지막 클릭에서 5초가 지난 뒤 자리비움 안내와 업데이트 소식을 코어 함수로 열면 두 창은 보이지만 `focus()`는 불리지 않았습니다.
- 타입 검사, lint, 단위 시험 669개, e2e 시험 26개가 통과합니다.

## 한계

- Windows 제목 표시줄의 ×와 끌기는 하네스로 누를 수 없어서 확인하지 못했습니다. `docs/checklists/windows-m0.md`에 항목을 더했습니다.
- Electron은 Windows에서 포커스를 받지 않는 창을 작업 표시줄에서도 뺍니다. 이제 11개 창도 설정이나 마이홈처럼 작업 표시줄에 단추가 생길 수 있습니다. 실제로 생기는지는 점검표에서 봅니다.
- Mac은 포커스를 받지 않는 창을 눌러도 앱이 앞으로 왔으므로(0032) 달라지는 점이 거의 없습니다.
