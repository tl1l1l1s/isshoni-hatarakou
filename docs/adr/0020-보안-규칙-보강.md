# 0020 보안 규칙 보강

날짜 2026년 10월 9일

코드 검토에서 나온 규칙 문제(R2, R3, M17, M19, M20)와 폰 앱 이름 길이 문제(M25)를 고쳤습니다. 0007과 0011에서 정한 keyedWrite 방식을 이 문서가 바꿉니다.

## 정한 것

- 폰 신호의 연결 키를 값에서 경로로 옮겼습니다. 예전에는 폰이 `mod/phone/u/{uid}/sig`에 키 `h`를 담아 썼습니다. 규칙은 쓰기 뒤의 노드 전체를 보므로 맞는 `h`가 이미 있으면 키를 모르는 사람도 `sig/open` 같은 하위 칸을 로그인 없이 쓸 수 있었습니다. 이제 폰은 `sig/{키}`에 쓰고 규칙은 경로의 키를 저장한 키와 비교합니다. 키를 모르면 어떤 칸에도 쓰지 못합니다.
- keyedWrite 템플릿은 `keyedWrite(keyPath, item)`이 되었습니다. 칸 아래 `$key`에 PC 실행 중 확인과 키 비교를 두고 item 규칙을 더합니다. 폰은 지우지 못하고 본인은 언제나 읽고 씁니다. PC 실행 중 표시는 예전처럼 `users/{uid}/presence/online`입니다.
- phone 규칙은 하위 칸만 고치는 쓰기에도 at이 서버 시각이기를 요구합니다. 그래서 열림 신호의 4시간 상한은 마지막으로 쓴 시각부터 잽니다.
- PC 앱은 `sig` 전체를 구독하고 지금 키의 칸만 읽습니다. 키 새로 만들기와 폰 연결하기는 새 키를 쓴 뒤 `sig`를 통째로 지웁니다. 새 키를 먼저 쓰므로 그 사이에 예전 키로 보낸 신호는 거부되고 지우기가 남은 칸을 정리합니다.
- 안내 페이지의 신호 주소는 `.../sig/{키}.json`이고 본문에는 키가 없습니다. QR 링크는 그대로입니다.
- 스스로 가입한 계정을 막습니다. 콘솔에서 이메일 가입을 막지 못한 경우에 대비해 규칙의 로그인 확인을 `users/{uid}/public/friendCode`가 있는지로 바꿨습니다(`rules/core.ts`의 `ISSUED`). friendCode는 계정 발급 스크립트만 만들고 규칙은 앱이 friendCode를 새로 만들거나 바꾸지 못하게 합니다. `scripts/create-account.ts`는 계정을 만들 때 항상 friendCode를 씁니다.
- 이 확인을 거치는 쓰기는 파일 올리기, 방 만들기, roster 참여, 본인 기록(users와 모든 모듈의 사용자 범위), 받은 기록 보내기입니다. 읽기는 공개 프로필, 친구 코드, config, catalog, files, 서버 조정값입니다.
- roster 확인(`IN_ROSTER`), 방 주인 확인(`ROOM_OWNER`), 친구 확인(`IS_FRIEND`)은 로그인만 봅니다. roster, 방 meta, 친구 목록은 발급 계정만 만들 수 있으므로 이 세 확인도 발급 계정만 통과합니다. photo 규칙 시험은 friendCode 없이 roster를 넣기 때문에 이렇게 두면 그 시험을 고치지 않아도 됩니다.
- 에뮬레이터 시험의 사용자에게는 `rules/tests/issued.ts`의 `issued(...)`로 friendCode를 넣습니다. adapter 계약 시험은 가입한 계정마다 관리자 토큰으로 friendCode를 씁니다.
- 지운 방에는 멤버가 새로 쓰지 못합니다. `roomMember` 템플릿의 쓰기와 방 범위 `dailyQuota`의 쓰기에 삭제 표시 확인을 더했습니다. 멤버는 지운 방의 기록을 지우기만 합니다.
- 방 주인은 지운 방에서도 지우기를 합니다. 주인 앱이 deleteWithRoom 컬렉션을 지운 뒤에 멤버가 쓴 기록이 남아도 주인이 지울 수 있습니다.
- 채팅 메시지 키는 15자리 숫자와 밑줄로 시작하고 키의 시각이 서버 시각보다 1분 넘게 앞서지 못합니다. 1분은 앱 시계 오차와 빠르게 보낼 때 1씩 더하는 시각을 받는 여유입니다. 지금 시각은 13자리라 앞에 00을 붙여 글자로 비교합니다. 이 비교는 2286년까지 맞습니다.
- 멤버 기록에 모양 검사를 더했습니다. look은 64자 16진수 해시이고 mods는 모듈 id마다 숫자입니다. m은 모듈마다 필드 값이 128자 이하 글, 숫자, 참거짓이거나 그런 값을 담은 한 단계 객체입니다. 키 이름은 32자까지이고 정하지 않은 필드는 받지 않습니다.
- 공개 프로필 이름은 20자(`NAME_MAX_LENGTH`)까지입니다. 앱의 닉네임 검사와 계정 발급 스크립트가 이미 같은 한도를 씁니다.
- 폰 앱 이름은 36자까지입니다. 머리 위 이름을 보내는 presence 기록은 모듈마다 128바이트까지인데 한글 40자 이름은 130바이트가 되어 보내기가 예외로 끝났습니다. 36자면 한글 이름도 118바이트입니다.
- 제어 문자처럼 JSON에서 길어지는 이름이 128바이트를 넘으면 이름 없이 보내서 머리 위에 폰에서 작업 중이 보입니다. 보낸 값 기록은 보내기가 끝난 뒤에 바꿉니다.

## 명세와 다른 점

- FOC-09는 머리 위 폰 앱 이름을 40자까지로 적었지만 36자로 줄였습니다. 이유는 위에 적었습니다.
- 예전 형식으로 만든 폰 자동화(`sig.json` 주소와 키를 담은 본문)는 이제 거부됩니다. 폰 연동은 0.1.1 다음에 들어가 아직 배포하지 않았으므로 예전 형식을 옮기는 코드는 두지 않았습니다.

## 알려진 한계

- 전체 범위 `dailyQuota('global')`(하루 촬영 한도)는 아직 로그인만 봅니다. 발급 확인을 더하면 photo 규칙 시험의 사용자에게 friendCode를 넣어야 하는데 photo 모듈은 이번 작업 범위 밖입니다. 합친 뒤 photo 시험에 `issued(...)`를 넣고 템플릿의 `who`를 `AUTH`로 바꾸면 됩니다.
- photo 조각은 쓰기 조건에 `t.roomMember()['.read']`를 써서 photo 쓰기에는 지운 방 확인이 들어가지 않습니다. `['.write']`로 바꾸면 들어갑니다. gacha는 자기 삭제 표시 `tomb/_room`으로 따로 막습니다.
- 규칙은 자식 수를 세지 못합니다. 멤버 기록의 m과 mods는 칸마다 크기만 막고 칸 수는 막지 못합니다. 모듈마다 128바이트 합계는 앱이 막습니다.
- 공개 프로필의 m(chat 이모티콘 목록, growth 레벨)은 모양을 검사하지 않습니다. 발급 계정만 쓰므로 그대로 두었습니다.
- 본인이 공개 프로필을 통째로 지우면 friendCode도 지워져 그 계정이 막힙니다. 앱은 필드만 고치는 update로 쓰므로 이렇게 지우는 경로가 없습니다.
- 발급 확인은 콘솔에서 이메일 가입을 끄는 일을 대신하지 않습니다. 스스로 가입한 계정도 로그인 토큰을 받고 Authentication에 계정이 쌓입니다.
- 실제 Firebase와 실제 폰 자동화로는 확인하지 않았습니다. 데이터베이스 에뮬레이터에서 규칙 시험, REST 쓰기, Chromium으로 연 안내 페이지의 신호 보내 보기를 확인했습니다.
