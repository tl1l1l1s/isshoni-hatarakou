# 0043 성능 다듬기

날짜 2026년 10월 16일

0025의 측정값과 코드 점검에서 찾은 최적화 후보 다섯 개를 고쳤습니다. 이 문서는 무엇을 왜 바꿨는지와 이 Mac에서 잰 값을 적습니다.

## 바꾼 것

1. **클릭 통과 확인 주기**
   - 지금까지는 커서가 실행 화면 창에서 40px 안에 있으면 8ms마다 커서를 읽었습니다. 이 창에는 좌석 사이와 위쪽의 투명한 곳도 들어 있습니다. 그래서 캐릭터 근처에서 펜으로 그리는 동안 확인이 계속 빠르게 돌았습니다.
   - 이제는 캐릭터, 칩, 메뉴 같은 클릭 영역에서 40px 안일 때만 8ms마다 읽습니다. 그 밖에서는 창 안이어도 50ms마다 읽습니다.
   - 클릭 영역 안이나 바로 옆에서는 전처럼 8ms마다 읽습니다. 그래서 캐릭터 위의 펜을 들어 옆 캔버스에 바로 내리는 경우는 그대로 막습니다.
2. **친구 이름 다시 읽기**
   - 공개 일정이 있는 친구의 이름을 1분마다 서버에서 다시 읽던 것을 30분마다로 늘렸습니다.
   - 그 친구의 공개 일정이 바뀔 때도 이름을 다시 읽습니다. 공개 일정이 없는 친구의 이름은 화면에 나오지 않아서 읽지 않습니다.
3. **뽀모도로 공유**
   - 방에 남은 분(`min`)을 분이 바뀔 때마다 쓰던 것을 단계마다 끝나는 서버 시각(`end`)을 한 번 쓰는 방식으로 바꿨습니다. 남은 분은 받는 PC가 서버 시각으로 계산합니다.
   - 분이 바뀌면 그 PC가 좌석 말풍선을 다시 그립니다. 서버 시각 보정이 바뀌어도 2초 안이면 다시 쓰지 않습니다.
   - 0.1.1 앱이 보내는 `min`도 그대로 읽습니다.
4. **그림 파일 디스크 캐시**
   - 캐릭터 그림 같은 파일을 메모리에만 담아 두어서 앱을 켤 때마다 서버에서 다시 받았습니다.
   - 이제 한 번 받은 파일을 렌더러의 IndexedDB에 계정마다 따로 남깁니다.
     - 파일 이름이 내용 해시라서 내용이 바뀌지 않습니다.
     - 읽을 때 해시를 다시 계산해 맞는 것만 씁니다.
     - 1,000개를 넘으면 오래전에 넣은 것부터 지웁니다. 파일 하나가 64KB 이하라 많아야 64MB쯤입니다.
   - 메인 프로세스 저장소는 메인 스레드에서 동기로 써서 커서 확인을 막을 수 있으므로 쓰지 않았습니다.
5. **효과 창 크기**
   - 효과 창은 모두 모니터 전체 크기였습니다. 창 버퍼는 창 크기에 비례합니다(0025).
   - 이제 화면을 가로지르는 효과(날리기, 채팅 날리기)만 모니터 전체 창을 씁니다. 이런 효과는 `EffectDecl.screen`을 켭니다.
   - 캐릭터 둘레에서 끝나는 효과(춤, 때리기, 폭탄)는 실행 화면 둘레만 덮는 창에 그립니다. 여백은 위 240px, 옆 120px, 아래 40px이고 모니터 밖으로는 자릅니다.
   - 메인 프로세스는 효과 창 영역을 창 이름마다 따로 기억합니다. 두 크기의 창이 동시에 열려도 영역이 섞이지 않습니다.

## 확인한 것

이 Mac에서 e2e 빌드를 켜고 확인했습니다.

- **클릭 통과 확인 주기:** 커서를 가짜 플랫폼으로 옮기고 커서를 읽은 횟수를 셌습니다.

  | 커서 위치 | 초당 읽은 횟수 | 메인 프로세스 CPU |
  |---|---|---|
  | 실행 화면 창 안의 투명한 곳 | 19.6번 (전에는 111번) | 0.72% |
  | 캐릭터 위 | 111.5번 | 2.19% |
  | 캐릭터 옆 30px | 111.1번 | 1.79% |

  `osclick.ts`를 세 번 실행해 세 번 모두 필수 항목이 통과했습니다. 캐릭터에서 빈 자리로 옮겨 20ms 뒤에 누르는 두 항목도 매번 5번 중 5번 통과했습니다. 참고 항목 두 개(실제 Mac 오버레이 창, 멀리서 바로 찍기)는 전처럼 실패합니다.
- **친구 이름:** 이름만 쓰면 3초 뒤에도 친구님 일정이었습니다. 공개 일정을 하나 더 쓰자 바로 가짜 친구님 일정으로 바뀌었습니다.
- **뽀모도로 공유**
  - 서버 시각을 이 PC보다 10분 앞당기고 1분 타이머를 시작했습니다. 방에 쓴 `end`는 서버 시각 기준 59초 뒤였습니다.
  - 가짜 친구의 `end`를 62초 뒤로 쓰자 머리 위가 집중 2분 남음으로 보였고 새로 쓰지 않아도 집중 1분 남음으로 바뀌었습니다.
  - 0.1.1 형식 `{ ph: 'b', min: 7 }`은 휴식 7분 남음으로 보였습니다.
- **그림 파일 디스크 캐시:** 파일을 올리고 한 번 읽은 뒤 앱을 다시 켰습니다. 메모리 서버가 비어서 서버에는 파일이 없었는데도 같은 내용을 읽었습니다.
- **효과 창 크기**
  - ▼ 메뉴 춤추기와 폭탄 던지기는 576x612 창에 그려졌습니다. 이 창은 실행 화면(336x372)을 둘러쌉니다. 춤 캐릭터와 날아가는 폭탄은 창 안에서 잘리지 않았습니다.
  - 채팅 날리기는 1512x982 모니터 전체 창에 그려졌습니다.
  - 같은 춤 효과를 두 크기의 창에 번갈아 세 번씩 그리고 footprint 합계를 비교했습니다. 모니터 전체 창은 효과 동안 244~255MB가 늘었고 실행 화면 둘레 창은 138~145MB가 늘었습니다.
- 타입 검사와 lint가 통과했습니다. 단위 시험은 뽀모도로 시험 2개를 더해 673개가 통과하고 e2e 시험 26개도 통과합니다. e2e는 두 크기의 효과 창을 모두 확인하도록 고쳤습니다.

## 한계

- Windows에서는 재지 않았습니다. 클릭 통과 비용과 효과 창 메모리는 Windows 배율과 GPU에 따라 다릅니다.
- 효과가 도는 동안의 합계는 2좌석 방에서 여전히 476~522MB라 400MB 목표를 넘습니다. 창을 하나 여는 것만으로 드는 몫(약 140MB)이 남기 때문입니다.
- 0.1.1 앱은 새 형식(`end`)을 읽지 못합니다. 그래서 업데이트하기 전까지는 새 앱 사용자의 뽀모도로 남은 시간이 0.1.1 앱 화면에 보이지 않습니다.
- 친구가 이름을 바꾸면 그 친구가 공개 일정을 바꾸기 전까지 길게는 30분 동안 옛 이름이 보입니다.
- 디스크 캐시에 남은 그림은 방을 나가거나 연결 해제를 해도 이 PC에 남습니다. 이미 화면에 보였던 그림만 남고 다른 계정으로 로그인하면 따로 둔 캐시를 씁니다.
- 실행 화면 둘레 효과가 도는 몇 초 사이에 실행 화면을 끌어 옮기면 효과는 원래 자리에서 끝납니다.
