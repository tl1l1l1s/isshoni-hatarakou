# 0037 QA 후속 연결

날짜 2026년 10월 11일

QA 수정 뒤 검증에서 연결과 도구 묶음 몫으로 남은 일곱 가지를 고쳤습니다. 연결된 채로 서버가 잠깐 거부한 뒤의 구독과 자동 재입장(RES-3), transaction 거부 글, 끊긴 동안의 친구 이름, 측정 도구의 잠듦 대기, 클릭 통과 폴링 비용, 시작 실패 화면, 다시 누르기 문구입니다. 고친 곳은 `src/renderer/server`, `RoomSession`과 `runtime.ts`, `types.ts`의 `OFFLINE`과 방 입장 계약, `main.tsx`, `clickthrough.ts`의 설명, friends 모듈, `measure.ts`, 시험과 검증 지도와 명세 줄입니다. 지적이 고칠 곳으로 짚은 rooms 모듈 자동 재입장과 같은 자동 입장인 status 모듈 자동 퇴장 뒤 돌아오기도 한 줄씩 고쳤습니다.

## 연결된 채로 거부당한 구독

규칙을 10초 거부했다 되돌리면 값 구독(문서 watch, 멤버)은 다시 걸렸지만 목록 구독(채팅 목록, 방 이벤트 같은 `watchList`, `watchEvents`)은 연결을 한 번 끊었다 이을 때까지 값을 하나도 받지 못했습니다. 에뮬레이터에서 SDK 기록을 켜고 원인을 찾았습니다.

- 서버는 거부한 구독마다 취소 메시지를 보냅니다. 목록 구독이면 그 메시지의 query가 `[{"i":".key","sin":true,"ein":true,"l":5,"vf":"r"}]`처럼 서버가 채운 모양입니다. firebase 12.19의 `onListenRevoked_`는 이 모양으로 구독을 찾는데 SDK가 보낸 query는 `{"i":".key","l":5,"vf":"r"}`라서 찾지 못합니다. 그래서 SDK는 cancel을 부르지 않고 계속 구독 중이라고 여깁니다. 서버는 그 구독에 값을 더 보내지 않고 다시 연결될 때 SDK가 구독을 다시 보내야 값이 다시 옵니다. 기본 구독(경로 하나의 값)은 query가 null이라 SDK가 찾습니다.
- 그래서 adapter는 모든 구독을 `listen`으로 겁니다. 거부로 끊기면 5초, 15초, 1분 뒤에 다시 걸고 그 뒤로는 5분마다 겁니다. 다시 연결되면 기다리지 않고 바로 겁니다.
- 목록 구독에는 같은 경로 아래 없는 자식 `~`의 값 구독을 짝으로 붙입니다. 이 자식은 데이터에 쓰지 않아서 값이 늘 null입니다. 읽기 규칙은 위에서 아래로만 열리고 지금 규칙에는 query 조건이 없습니다. 그래서 목록 경로가 거부되면 이 자식도 같은 규칙 평가에서 거부되고 SDK가 짝 구독의 cancel을 부릅니다. 둘 가운데 하나가 끊기면 둘 다 해제하고 함께 다시 겁니다. 목록 구독을 해제했다가 다시 걸면 SDK가 서버에 구독을 새로 보내므로 아직 거부 중이면 그 응답으로 cancel이 옵니다.
- 계정 접속 상태 구독도 `listen`을 씁니다. 상대가 나를 친구로 두지 않았거나 서버가 거부해 전체 읽기가 끊긴 동안에는 online과 lastSeen만 따로 구독하고 전체 읽기는 같은 간격으로 다시 걸어 봅니다. 전체 읽기가 다시 되면 따로 건 구독을 해제합니다. 전에는 따로 건 구독도 거부되면 그대로 멈췄습니다.
- 비용은 목록 구독마다 값이 null인 구독 하나입니다. 앱 하나에 목록 구독이 열 개 남짓입니다. 거부가 풀린 뒤에는 목록 구독마다 목록을 한 번 다시 받습니다.

고르지 않은 방법도 적어 둡니다.

- SDK 안의 `onListenRevoked_`를 덮어쓰는 방법은 공개하지 않은 이름에 기대므로 SDK 버전을 올리면 경고 없이 동작이 멈출 수 있습니다.
- 거부가 오면 연결을 끊었다 잇는 방법은 연결이 끊길 때의 삭제 예약이 실행되어 친구 화면에서 좌석과 접속 표시가 잠깐 사라집니다.
- 모든 목록 구독을 몇 분마다 다시 거는 방법은 거부가 없어도 목록을 계속 다시 받습니다.
- SDK 기록(`enableLogging`)으로 취소 메시지를 보는 방법은 전역 설정이고 모든 메시지를 문자열로 바꿉니다.

## 자동으로 다시 들어가기

앱을 켤 때의 자동 재입장은 실패하면 다음에 연결될 때만 다시 들어갔습니다. 연결된 채로 서버가 거부하면 연결 이벤트가 없어서 규칙이 풀린 뒤 90초가 지나도 방에 들어가지 않았습니다. 절전 뒤 다시 들어가기와 `여기서 계속 쓰기`는 다시 시도가 아예 없었습니다.

- `ctx.room.join(code, { retry: true })`를 더했습니다. 연결된 채로 서버가 거부해 `network`로 실패하면 RoomSession이 5초, 15초, 1분 뒤에 다시 들어가고 그 뒤로는 5분마다 들어갑니다. 다른 입장, 나가기, 절전이 있으면 입장 번호가 바뀌어 다시 시도를 멈춥니다. 돌려주는 것은 첫 시도의 결과라서 부른 쪽은 안내를 한 번만 띄웁니다.
- 앱을 켤 때의 자동 재입장(rooms 모듈), 절전 뒤 다시 들어가기, `여기서 계속 쓰기`, 자동 퇴장 뒤 돌아오기(status 모듈)가 retry로 들어갑니다. 사용자가 코드나 친구 창이나 초대로 들어갈 때는 다시 시도하지 않고 이유를 보입니다.
- 끊긴 동안의 입장은 전처럼 연결될 때까지 기다리므로 rooms 모듈의 연결 이벤트 다시 시도는 뺐습니다.
- 다시 시도를 rooms 모듈에만 두면 코어가 부르는 절전 뒤 다시 들어가기와 `여기서 계속 쓰기`에는 다시 시도가 없어서 RoomSession에 두었습니다.

## 백그라운드 프로필 쓰기

같은 에뮬레이터 검사에서 거부 중에 켠 앱이 처리하지 않은 거부를 하나 냈습니다. `ctx.self.setProfile`이 쓰기 Promise의 실패를 처리하지 않아서 growth 모듈이 켤 때 쓰는 레벨이 거부되면 자동 오류 보고가 생겼습니다. 계정 접속 상태 쓰기처럼 로그에 `프로필 쓰기 실패`를 남기게 했습니다.

## transaction 거부 글

SDK는 set과 update의 거부를 code `PERMISSION_DENIED`로 알리지만 transaction의 거부는 code 없이 message `permission_denied`로만 알립니다. 그래서 방 만들기(`createMeta`)와 `docs.transaction`을 쓰는 모듈 쓰기(가챠 뽑기 등)의 거부가 인터넷 연결 안내로 보였습니다. `writeError`가 code와 message(대소문자 무시)를 함께 보고 거부면 `WRITE_DENIED`와 code `PERMISSION_DENIED`를 줍니다. 원래 오류는 그대로 `cause`에 있습니다.

## 끊긴 동안의 친구 이름

친구 창은 친구 줄을 그릴 때 공개 프로필을 읽어 이름을 보입니다. Firebase 읽기는 연결될 때까지 끝나지 않아서 끊긴 채로 연 창은 `이름 없음 확인하는 중`을 보였고 다시 연결된 직후에도 잠깐 `이름 없음 접속 중`이었습니다. 친구 이름이 바뀐 것처럼 보였습니다.

- friends 모듈이 읽은 이름을 계정 로컬 기록 `names`(uid마다 이름)에 남깁니다. 프로필을 읽기 전에는 이 이름을 보이고 본 적이 없으면 `친구`를 보입니다. `친구`는 친구 알림과 일정이 이름을 모를 때 이미 쓰는 말입니다.
- `이름 없음`은 읽은 프로필에 이름이 없을 때만 보입니다. 그때는 남긴 이름도 지웁니다.
- 끊은 친구의 이름은 지우지 않습니다. 목록에 없는 사람의 줄은 그리지 않아서 보이지 않고 사람마다 이름 하나라 기록은 작습니다.

## 클릭 통과 폴링

커서가 스테이지 40px 안에 머물면 8ms마다 커서를 읽습니다. M5에서 초당 111번 읽고 메인 CPU는 1.75%입니다(멀리 있으면 19.6번에 0.5%). 16ms로 바꾸면 59번에 1.2%였지만 캐릭터 위의 커서를 옮겨 20ms 뒤에 누르는 osclick 검사가 두 번째 실행에서 머리 위 5번 중 4번만 통과했습니다. 세 번 모두 5번을 통과해야 바꾸기로 했으므로 8ms를 그대로 두고 잰 값과 까닭을 `clickthrough.ts`의 ponytail 설명에 적었습니다. Windows 비용은 재지 않았습니다.

## 시작 실패 화면

시작하지 못하면 화면에 `시작하지 못했어요. ` 뒤로 영어나 코드일 수 있는 원래 글이 붙고 할 일 안내가 없었습니다. 이제 화면에는 `시작하지 못했어요. 앱을 다시 켜 주세요.`만 보이고 원래 글은 전처럼 메인 로그와 자동 오류 보고(`renderer.boot`)에 남습니다. 글을 확인하다 보니 투명한 스테이지 창 위에 검은 글자만 있어 어두운 바탕화면에서는 읽기 어려웠고 좁은 창에서 `다시`가 두 줄로 나뉘었습니다. 그래서 실행 화면 알림과 같은 유리 판(`stage.module.css`의 `toast`)에 올렸습니다.

## 다시 누르기

용어 정리에 맞춰 코어의 끊김 글 세 개(`OFFLINE`, 닉네임 저장, 방 지우기)의 끝을 `연결되면 다시 해 주세요.`에서 `연결되면 다시 눌러 주세요.`로 바꿨습니다. 모듈 글은 문구 묶음이 바꿉니다. 0033에 적힌 옛 글은 기록이라 그대로 둡니다.

## 측정 도구

잠듦 확인을 15초까지 기다립니다. 잠들기까지 5초 남짓 걸려서 기본 5초 대기로는 절반쯤 실패했습니다. 문구 정리 뒤 처음으로 `measure.ts --soak 60`을 두 번 끝까지 돌렸고 다른 단계는 고칠 것이 없었습니다.

- new/transaction-denied-text. transaction 거부 글 절입니다.
- new/friends-offline-name. 끊긴 동안의 친구 이름 절입니다.
- new/measure-asleep-wait-flaky. 측정 도구 절입니다.
- new/clickthrough-near-poll-cost. 클릭 통과 폴링 절입니다. 값은 그대로이고 설명만 더했습니다.
- new/src/renderer/main.tsx:9. 시작 실패 화면 절입니다.

## 확인한 것

- 에뮬레이터에서 SDK 기록을 켜고 규칙을 거부로 바꿔 서버의 취소 메시지 모양과 SDK가 기본 구독에만 cancel을 부르는 것을 봤습니다.
- 계약 시험에 연결된 채로 거부당한 구독과 자동 재입장 시험을 더했습니다. 고치기 전 코드에서는 값 구독만 다시 걸리고 목록 구독에서 실패합니다. 이 클라이언트가 쓰면 SDK가 자기 캐시로 바로 알려 서버가 구독을 끊은 것이 보이지 않으므로 값은 규칙 밖에서 씁니다. transaction과 방 만들기의 거부 글도 계약 시험이 두 서버에서 봅니다.
- 검증 묶음의 RES-3 에뮬레이터 시험을 이 작업 트리로 돌렸습니다. 방에 둘이 있는 채 규칙을 10초 거부했다 풀면 쓰다듬기가 12.0초 뒤에 닿고(전에는 60초 동안 하나도 닿지 않음) 거부 중에 켠 앱은 풀린 뒤 10.0초에 방에 들어갑니다(전에는 90초 동안 들어가지 않음). 처리하지 않은 거부도 없어졌습니다.
- 에뮬레이터를 가리키는 빌드로 친구 창을 끊긴 채로 열었습니다. 고치기 전에는 처음과 이름을 본 뒤 모두 `이름 없음 확인하는 중`이었습니다. 고친 뒤에는 처음에 `친구 확인하는 중`, 이름을 본 뒤에는 `비친구 확인하는 중`이고 다시 연결될 때 `이름 없음`을 거치지 않습니다.
- 단위 시험을 더했습니다. `writeError`의 두 거부 모양, RoomSession retry의 간격과 나가기로 멈추기, 거부된 프로필 쓰기의 로그(고치기 전 코드에서는 처리하지 않은 거부로 실패), 친구 이름 기록입니다.
- verify-isshoni로 절전 뒤 서버 거부를 흉내 내면 안내가 한 번 뜨고 거부를 풀면 첫 실패 5.4초 뒤에 다시 들어가는 것을 봤습니다. 끊긴 채로 한 닉네임 저장, 쓰다듬기, 채팅, D-day 추가의 새 끝맺음과 부팅 실패 화면은 넓은 글꼴 흉내와 두 테마로 봤습니다. 방 지도의 지운 방 안내는 앱이 보이는 `주인이 지운 방이에요.`로 고쳤습니다.
- `measure.ts --soak 60`을 두 번 끝까지 돌렸고 `errors.json`은 둘 다 비었습니다. 16ms 폴링 osclick은 두 번 돌렸고 8ms 최종 빌드는 세 번 돌렸습니다. 최종 빌드의 첫 실행에서 첫 단계(빈 자리 옮겨 누르기)가 한 번 실패했고 이어 돌린 두 번은 참고 항목 말고 모두 통과했습니다.
- `npm run typecheck`, `npm run lint`, `npx vitest run`, `npm run rules:build -- --check`, 에뮬레이터 시험 전체(19개 파일, 9800번대 포트), e2e 26개가 통과했습니다.

## 한계

- 목록 경로 바로 아래 자식에 읽기를 따로 여는 규칙이 생기면 그 규칙이 짝 구독의 `~`에 열리지 않는지 봐야 합니다. 그 규칙이 `~`에 열리면 목록 구독만 거부되고 짝 구독은 그대로라 전처럼 목록 구독이 멈춥니다. 지금 규칙의 `in/$sender`는 uid가 `~`인 사람이 없어서 열리지 않습니다. query 조건 규칙(`query.limitToLast` 같은 것)을 쓰면 반대로 짝 구독이 먼저 거부될 수 있습니다.
- 서버의 취소 메시지 모양은 에뮬레이터에서만 봤습니다. 짝 구독은 기본 구독이라 실제 서버가 query를 어떤 모양으로 보내도 SDK가 cancel을 부릅니다.
- 다시 걸기와 다시 들어가기의 간격은 5분까지 늘어납니다. 거부가 길었으면 풀린 뒤 5분까지 기다릴 수 있습니다.
- 자동 입장의 다시 시도는 끝이 없습니다. 규칙이 계속 거부하면 5분마다 읽기를 두세 번 보냅니다.
- 상대가 아직 나를 친구 목록에 넣지 않은 친구 줄은 친구 창이 열려 있는 동안 접속 상태 전체 읽기를 5분마다 한 번 거부당합니다. 개발자 콘솔에 경고가 한 줄씩 남습니다.
- 앱 파일이 서로 맞지 않을 때의 글(`boot.tsx`)도 투명한 창 위에 글자만 있지만 이번 지적 밖이라 그대로 두었습니다.
- Windows에서는 폴링 비용과 새 화면을 보지 않았습니다.
